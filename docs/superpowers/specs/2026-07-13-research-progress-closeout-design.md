# 研究进度收口设计

## 背景与目标

公司研究资产正在由批处理脚本和多个研究 agent 并行产出。当前公司目录中的有效报告数量已经显著高于 `coverage/cn-a/research_queue.jsonl` 中的 `completed` 数量，`research/index.json` 等生成文件也落后于实际资产。与此同时，现行严格校验把大量格式差异和扩展元数据都视为错误，导致审计结果不能准确区分“资产不可用”和“格式尚未统一”。

本次收口的目标是：建立可重复、可审查的覆盖队列对账机制；恢复生成文件与公司资产的一致性；将公司资产校验划分为真正阻塞消费的基础错误与可逐步治理的规范问题；不覆盖任何历史研究报告。

## 根因

`automation/scripts/batch_research.py` 在自己的执行路径中会更新队列，但其他研究 agent 可以直接创建报告和 `meta.json`，并不一定同步更新同一个 JSONL 队列。多个进程还可能在共享工作区内先后写入资产和队列。因此，公司目录是研究结果的事实来源，而队列是可能暂时滞后的工作状态记录。

生成文件依赖所有公司资产先通过基础校验。单个无效 `meta.json` 会阻止索引重建，批处理对重建子进程的失败又没有形成足够醒目的最终错误，最终造成索引长期停留在较早批次。

严格校验于批量研究进行期间引入，但报告模板、历史报告和不同研究类型没有同步迁移。其规则把标题标点、分析师行写法、额外元数据字段和统一章节集合都作为硬错误，因而无法作为研究资产整体健康度的有效门槛。

## 对账命令

新增命令：

```bash
python -m trading_os coverage reconcile --check
python -m trading_os coverage reconcile --apply
```

命令读取覆盖队列和 `research/companies/`，以公司基础校验通过且 `latest_report` 实际存在为完成证据。

`--check` 只输出差异摘要和逐项变化，不写文件；存在差异时返回非零退出码，便于人工检查和自动化验证。`--apply` 只应用相同的、已经展示过的确定性变化：

- 将 `pending`、`running` 或 `failed` 且已有有效研究资产的条目更新为 `completed`；
- 把 `result_path` 设置为对应 `meta.json` 的 `latest_report`；
- 清空已经失效的 `failure_reason`；
- 为缺失的完成时间使用 `meta.json.updated_at`，不伪造当前执行时间；
- 保留原有 `started_at`、任务类型、优先级、原因和 agent 信息；
- 不反向降级已经完成的条目；
- 不修改 `needs_review`、`skipped` 等人工决策状态；
- 不修改任何公司报告或 `meta.json`；
- 遇到无效公司资产时报告阻塞项，但不把它标记为完成。

对账写入继续使用已有的排序和 JSONL 序列化逻辑，结果必须幂等：连续执行两次，第二次应无差异。

该命令是批次结束后的安全网，不替代研究流程自身更新队列的责任。项目文档将要求完整研究迭代在报告与 `meta.json` 完成后同步队列，并在批次收尾运行对账检查。

## 校验分层

基础校验继续作为索引、复核计划和价格提醒生成的硬门槛，覆盖以下机器可消费不变量：

- 公司目录、市场、代码和 symbol 一致；
- 状态和当前评级属于允许集合；
- `current_thesis`、估值区间、仓位计划和触发器结构有效；
- `latest_report` 与 `report_history` 指向公司目录内真实、不可变的 Markdown 报告。

严格审计调整为结构化输出，不再把所有规范问题混成同一种失败：

- 扩展元数据字段保留在审计信息中，不作为严格失败；这些字段可能承载质量评级、估值评级和跟踪指标等有效研究信息。
- 标题没有逐字匹配标准模板时记为风格警告，不使资产失效。
- 分析师标注缺失或不透明时记为来源追踪警告；未来模板继续要求具体工具和模型，但历史资产不因此失效。
- 日期和研究类型仍是严格结构要求，因为它们决定时间线和按类型解释报告。
- 章节要求按研究类型区分：`initial` 要求完整初始研究核心章节；`followup` 要求上一轮判断复盘、新信息、判断变化、跟踪触发器、风险和来源，不要求重复全部公司与行业背景。
- 无法识别研究类型的报告给出明确严格问题，不猜测类型。

本次不批量重写历史报告。由于报告不可变，历史缺陷只通过审计呈现；需要更新判断时创建新的 follow-up 报告，并按新规范产出。

## 错误处理与并行约束

对账在计算完整变更集后一次写入队列。任何 JSONL 解析错误、公司基础校验错误或参数冲突都必须产生清晰诊断。`--check` 和 `--apply` 必须互斥且至少指定一个，避免默认产生写操作。

最终对账和生成文件重建只能在当前并行研究批次稳定后执行。实现阶段不得暂存或提交其他 agent 的研究报告、来源文件或已有生成文件修改；生成文件只在最终收口时由本次命令重新生成并单独核对。

## 测试与验收

自动化测试覆盖：

- 检出“待处理但已有有效报告”的漂移；
- `--check` 不写文件且用退出码表达漂移；
- `--apply` 只执行允许的单向状态变化并补齐路径；
- 人工状态不被覆盖；
- 无效资产不被误标完成；
- 第二次对账无变化；
- 初始研究与跟踪研究使用不同章节规则；
- 扩展元数据和标题差异只产生警告；
- 基础资产不变量仍然阻止生成文件构建。

最终验收依次运行公司资产审计、覆盖层校验、对账检查、索引重建、复核计划构建、价格提醒构建和完整测试套件。暂存后必须用 `git diff --staged` 确认提交仅包含本次设计、代码、测试、必要文档、明确修复的阻塞元数据以及本次重建的生成文件。
