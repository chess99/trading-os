# CANSLIM Daily System Vendor and Data Source Review

Date: 2026-06-14

## Scope

This memo supports the CANSLIM daily research system design. It focuses on the pieces that
make the workflow stable in production:

- Which external projects are worth borrowing from.
- Which data providers should back daily screening, deep research, backtests, and alerts.
- Which parts of the current implementation are enough, and which are still design-level only.
- A practical rollout path from the current local system to a reliable daily operating system.

## Current Implementation Audit

Implemented and tested:

- `research daily-canslim` resolves an effective trading date, runs CANSLIM screening, deep
  researches strict candidates, writes decisions, updates `watchlist_state`, exports
  `artifacts/watchlist/state.json`, and writes a human report under `artifacts/research/`.
- `alert monitor --mode watchlist --once` evaluates watchlist symbols only, deduplicates alerts
  by cooldown key, writes `alerts`, and appends `EventLog` entries.
- `DataHub` supports provider routing, cache-first/offline/lazy-fill/refresh policies, and
  records provider failures through `provider_health`.
- `ResearchStore` now has datasets for decisions, watchlist state, alerts, technical setups,
  provider health, estimates, and news.
- Guard tests cover strict/provisional semantics, watchlist closure, stale alert state, and
  deep-research downgrade behavior.

Still incomplete for the target operating model:

- The production provider stack is not strong enough. `AkshareResearchProvider` is still the
  default live provider and does not provide point-in-time fundamentals suitable for serious
  factor research and backtesting.
- Deep research packets are structurally generated, but many dimensions can remain missing:
  institutional sponsorship, peer comparison, management guidance, business segments, and
  announcement/news evidence depend on provider coverage.
- Alerting is single-shot CLI only. There is no durable notification delivery layer, trading
  session loop, retry policy, or user-selected destination.
- Technical setup detection is a conservative placeholder. It defines pivot, buy zone, and stop
  levels, but it does not yet detect CANSLIM base patterns with proper volume confirmation.
- The workflow is not yet tied to a recurring automation. Manual command execution works; daily
  hands-off operation still needs an external automation or local long-running service.

## Vendor Findings

The vendor repositories are gitignored references. On 2026-06-14, `git fetch` was attempted for
all local vendor repositories. GitHub connectivity timed out for some repositories; others fetched
enough metadata to show the local snapshots are behind upstream. This means vendor code is useful
as design reference, but should not be a runtime dependency or copied wholesale.

### daily_stock_analysis

Useful patterns:

- Multi-source data manager with per-market fallback ordering.
- Degraded-but-not-empty reporting: partial analysis is marked as partial instead of hidden.
- Rich notification channel support.
- Agent pipeline split into technical, intelligence, risk, specialist, and decision stages.

Avoid copying:

- Large all-in-one service modules.
- UI-driven scheduler settings as the primary operating mechanism.
- LLM-first final decisions without deterministic evidence gates.

Adopt in Trading OS:

- Keep deterministic recipes as the first layer.
- Add a notification router similar in spirit, but driven by alert records and EventLog.
- Add partial report status fields to every deep research packet.

### TradingAgents / TradingAgents-CN

Useful patterns:

- Analyst role decomposition: market, fundamentals, news, social/event, bull/bear debate, risk,
  final manager.
- Per-step observability and explicit decision trace.
- Data fallback and tool fallback are first-class concepts.

Avoid copying:

- LLM agents as the primary data-processing layer.
- Final numeric targets that are generated by the model without deterministic valuation inputs.
- Heavy graph orchestration before the deterministic recipe layer is stable.

Adopt in Trading OS:

- Use multi-agent style only above the evidence layer: summarize evidence, argue bull/bear cases,
  and explain risk.
- Keep valuation, technical setup, watchlist transition, and alert firing deterministic.

### go-stock

Useful patterns:

- Local desktop-friendly alerting and DingTalk-style notification integration.
- Tool registry and prompt template concepts.
- Company announcement and news tooling.

Avoid copying:

- Browser crawler dependency as a core provider.
- In-memory task/alert state.

Adopt in Trading OS:

- Store notification attempts as append-only events.
- Add explicit announcement/news adapters, but keep provider failures visible.

### Qbot and ai_quant_trade

Useful patterns:

- Separation of data, strategy, execution, and risk layers.
- Backtest and paper-trading concepts.
- YAML/config driven strategy definitions.

Avoid copying:

- Broad platform scope before daily CANSLIM is reliable.
- Backtest examples with potential information leakage.

Adopt in Trading OS:

- Keep `RiskManager` and `EventLog` mandatory for backtest/paper paths.
- Add point-in-time checks before expanding factor/backtest claims.

## External Data Source Findings

### RQData

RQData is the best fit for the target architecture if paid access is acceptable.

Official RQData documentation states that it covers China A-share basic information, more than
10 years of historical daily/minute/tick行情, real-time tick/minute行情, and all financial data
since listing. It also documents A-share APIs for financial data, announcements, north/southbound
funds, margin financing, industry classification, and alternative data such as consensus estimates,
news sentiment, and ESG. More importantly, its A-share financial documentation explicitly says the
financial processing considers actual historical disclosure time to avoid future data in factor and
strategy testing.

Sources:

- https://www.ricequant.com/doc/rqdata/python/index-rqdatac
- https://www.ricequant.com/doc/rqdata/python/stock-mod.html

Decision:

- Target primary provider for production-quality daily research, factor research, and backtesting.
- Implement behind `DataHub` as `RqdataResearchProvider`.
- Require credentials before enabling in production; do not make tests depend on paid access.

### Tushare Pro

Tushare is the pragmatic first paid/semi-paid provider because setup is simple and Python SDK/HTTP
access are straightforward. Official documentation describes both HTTP POST access and Python SDK
access via token. It also documents permission tiers: many common endpoints use points; some
interfaces, including minute data, news sentiment, and announcements, need separate permissions.
Financial endpoints such as income, balance sheet, cashflow, forecast, express, dividend,
`fina_indicator`, `fina_audit`, `fina_mainbz`, and `disclosure_date` require at least 2000 points.

Sources:

- https://tushare.pro/document/1?doc_id=130
- https://tushare.pro/document/1?doc_id=131
- https://tushare.pro/document/1?doc_id=108
- https://tushare.pro/document/1?doc_id=234
- https://tushare.pro/document/1?doc_id=290

Decision:

- Recommended first adapter to implement because it can fill many current gaps quickly.
- Use for daily bars, trade calendar, stock basic, daily basic, financial statements, business
  segment composition, disclosure calendar, shareholder/holder fields where permission allows.
- Treat minute data, announcements, and news as optional paid sub-capabilities.
- Do not treat Tushare alone as point-in-time proof for backtests unless publish-date fields are
  carried through `ResearchStore`.

### JQData / JoinQuant

JQData is a viable paid alternative. Official JoinQuant material describes JQData/jqdatasdk as a
local Python data interface, usable outside the JoinQuant website/client, and covering A-share
price, fundamentals, futures, options, funds, factor library, finance queries, and HTTP-JQData.
Community documentation shows typical use of `get_price`, `get_bars`, `get_fundamentals`,
`finance.run_query`, `jy.run_query`, and macro queries.

Sources:

- https://www.joinquant.com/help/api/help?name=JQData
- https://www.joinquant.com/view/community/detail/5e4d0eac18d9ddb774452a7eb8f58bd4
- https://www.joinquant.com/api

Decision:

- Keep as second paid option if RQData cost or onboarding is not acceptable.
- Strong for research/backtest users already familiar with JoinQuant.
- Adapter should normalize JoinQuant codes into `SSE:600000` / `SZSE:000001` symbols and keep
  as-of/publish-date semantics explicit.

### AkShare

AkShare remains valuable as a broad free fallback. Official documentation lists extensive A-share
coverage: realtime/historical行情, peer comparison, business segments, announcements, news,
research reports, financial statements, shareholder/holder data, institutional holdings,
estimates, board/industry data, hot stocks, and technical screens.

Sources:

- https://akshare.akfamily.xyz/data/stock/stock.html

Decision:

- Keep as free fallback and exploratory data source.
- Use exact interface-level provenance in manifests because upstream pages can change.
- Do not use as the only source for formal trading advice or backtest proof.

## Recommended Provider Architecture

Implement provider priority by capability, not by provider name:

| Capability | Production target | Short-term pragmatic | Free fallback |
| --- | --- | --- | --- |
| trading calendar | RQData | Tushare | AkShare/exchange calendar |
| universe | RQData | Tushare stock_basic | AkShare |
| EOD quote snapshot | RQData | Tushare daily/daily_basic | AkShare/EastMoney |
| daily bars | RQData | Tushare daily + adj_factor | AkShare/BaoStock |
| fundamentals | RQData PIT financials | Tushare reports + publish dates | AkShare |
| business segments | RQData / announcements | Tushare fina_mainbz | AkShare |
| estimates | RQData alternative data | Tushare where available | AkShare/EM |
| news/announcements | RQData alternative data | Tushare paid/news permission | AkShare/CNInfo/Search |
| institutional sponsorship | RQData | Tushare holders/funds | AkShare holders/funds |
| realtime watchlist quote | RQData realtime | Tencent/Sina/EastMoney | AkShare realtime |

Provider router rules:

- Required daily capabilities: calendar, universe, EOD quote, daily bars, fundamentals.
- Required deep research capabilities: fundamentals, bars, business segments, news/announcements,
  estimates or valuation snapshot.
- Optional but confidence-affecting capabilities: institutional sponsorship, peer comparison,
  management guidance, industry crowding.
- If required daily capabilities fail, the recipe fails explicitly.
- If deep research capabilities fail, the affected symbol decision is downgraded to
  `research_only` and the report states the missing evidence.
- If optional capabilities fail, the report reduces confidence but may still classify as
  `wait_for_breakout` when core CANSLIM and setup evidence are complete.

## Stable Daily Operating Design

The daily system should run as three deterministic jobs:

1. `data close`
   - Resolve completed trading day.
   - Refresh calendar, universe, EOD quote, and required incremental fundamentals.
   - Record provider health and exact-date coverage.

2. `research daily-canslim`
   - Run full A-share screen.
   - Process all strict candidates.
   - Generate all strict deep research packets.
   - Downgrade any failed/incomplete packets before watchlist update.
   - Refresh active watchlist symbols.
   - Write daily report and `artifacts/watchlist/state.json`.

3. `alert monitor`
   - During trading sessions, monitor only `watching` and `actionable` watchlist symbols.
   - Use realtime quotes from a realtime-capable provider.
   - Fire deterministic triggers and write notification attempts.

Agent behavior:

- The agent should not decide data-fetch order ad hoc.
- The agent should run recipes, read manifests/reports, and explain outcomes.
- The agent may create bull/bear/risk explanations from evidence after deterministic data is
  complete.

## Notification Design

The next implementation should add a `Notifier` abstraction:

```text
notify(alert) -> delivery_result
```

Initial destinations:

- local terminal/stdout for tests.
- macOS notification or Codex thread heartbeat for local use.
- Feishu or DingTalk webhook for practical mobile delivery.

Every delivery attempt must write:

- alert id
- destination
- payload summary
- success/failure
- error message
- sent_at

The alert monitor should never mark an alert delivered merely because it was generated.

## Technical Setup Upgrade

Current setup detection uses the 60-day high as pivot. That is acceptable as a placeholder but not
as a mature CANSLIM base detector.

Upgrade path:

1. Keep the current pivot detector as `simple_60d_high_breakout`.
2. Add `base_type`:
   - `cup_with_handle_candidate`
   - `flat_base_candidate`
   - `double_bottom_candidate`
   - `high_tight_flag_candidate`
   - `simple_60d_high_breakout`
3. Add minimum quality checks:
   - base length
   - depth
   - price contraction
   - volume dry-up
   - breakout volume vs 50-day average
   - no excessive extension above pivot
4. Keep unrecognized setups as `research_only`, not `wait_for_breakout`.

## Recommended Roadmap

### Phase A: Provider hardening

- Add `TushareResearchProvider`.
- Add provider config with priority, token presence, proxy, timeout, and rate limit.
- Add exact-date coverage checks and provider health summary in manifests.
- Add tests with fake provider priority and stale cache cases.

### Phase B: Research depth

- Split company research into deterministic sections:
  - financial quality
  - segments and moat
  - institutional sponsorship
  - news and announcements
  - peer comparison
  - valuation
  - technical setup
  - decision packet
- Add `ResearchCompleteness` scoring. A packet is complete only when core sections have evidence.

### Phase C: Notification and automation

- Add `notifier.py`.
- Add `alert delivery` dataset or EventLog event type.
- Add recurring heartbeat/automation recipe outside the old scheduler.
- Add CLI dry-run and once modes.

### Phase D: RQData/JQData adapter

- Add `RqdataResearchProvider` or `JqdataResearchProvider` once credentials are available.
- Add point-in-time tests for financial data.
- Re-run CANSLIM, factor, and backtest recipes on the same provider stack.

## Acceptance Criteria for "Stable Enough"

The system should not be called stable until all of these are true:

- A daily command can run on the latest completed trading day without full-market per-symbol bars
  refresh.
- Every strict candidate produces a deep research packet with a machine-readable completeness
  status.
- Every strict or watched symbol receives exactly one current decision.
- Watchlist updates cannot promote a symbol to `watching` without complete deep research evidence.
- Alert monitor cannot scan full market and cannot fire from stale watchlist state.
- Daily report explicitly lists provider health, missing evidence, degraded dimensions, and
  confidence impact.
- Provider router has at least one paid/semi-paid source and one free fallback for core daily
  capabilities.
- Notification delivery is separately auditable from alert generation.
- Full test suite covers stale cache, provider fallback, incomplete research, watchlist state
  transitions, and alert deduplication.
