# 简化研究流程

## 目标

这套流程把“全市场重新跑一遍”改成两段式系统：先完成一次全市场基线判断，之后只处理新增公司、重大变化和每日收盘价格触发。

核心原则只有三个：

1. 主 Agent 负责批量浏览全市场，判断哪些公司值得占用研究资源。
2. 只有确实需要研究的公司才派单公司 Agent；一家公司由一个 Agent 从头做到尾。
3. 研究结论沉淀为当前状态、自选池和触发条件，后续按变化增量维护。

## 当前事实源

- `coverage/cn-a/research_state.jsonl`：全市场公司当前状态，一家公司一行。
- `coverage/cn-a/event_scan_state.json`：公告扫描最后成功时间和近期稳定公告 ID。
- `research/watchlist.jsonl`：从当前状态派生的自选池和触发条件。
- `research/companies/CN/{ticker}/current.md`：做过正式研究的公司只保留一份当前报告。
- 运行队列：只保存尚未完成的当前任务，任务结束后不充当研究档案。

公司长期状态使用：

- `unseen`：尚未完成基线判断。
- `ignore`：目前不值得继续投入研究资源，只保留简短理由；若有明确的公司特定重看条件再补充。
- `watch`：值得观察，等待价格、财报、公告或其他明确条件。
- `researched`：已经完成正式研究，报告和触发条件仍有效。

`research_now` 是主 Agent 的派发决定，不是长期状态。单公司研究完成后，最终落到 `ignore`、`watch` 或 `researched`。

持仓属于用户账户信息，不混入研究状态。

## 一次性全市场基线

首次建立基线时，冻结股票范围、证券身份和信息截止时间。主 Agent 分批浏览全市场压缩材料，并对每家公司给出一个判断：

- `ignore`：商业质量、治理、财务、估值或可理解性明显不足，当前不值得单独研究。
- `watch`：有值得保留的线索，但应等待更合适的价格或更关键的信息。
- `research_now`：现有信息显示机会或关键不确定性值得单独研究。

主 Agent 应关注公司如何赚钱、竞争优势是否可信、利润能否变成股东现金流、资产负债表和治理风险、当前价格隐含了什么，以及什么变化会推翻判断。程序可以整理事实和公告，但不能替主 Agent 作投资判断。

这里不设置“必须研究多少家”的数量目标，也不因为某个行业、市值区间或既有标签机械派发。A 股中真正值得正式研究的公司可能只是数百家，也可能随市场和信息变化；实际数量由主 Agent 逐家公司判断。大多数明显不值得投入的公司在这一层结束，不为它们创建单公司任务或冗长报告。

批量判断只更新全市场状态，不为每家公司生成 Markdown 报告。研究是否继续也不能由固定年化收益率门槛机械决定。

基线写入只接受当前状态仍为 `unseen` 且尚未做过 baseline 判断的公司；一批判断中只要混入一家已经判断过的公司，整批拒绝且不留下部分更新。基线完成后，不再周期性重跑整套全市场流程。新增上市公司只补做新增部分；已有公司的后续处理使用 `event` 模式进入增量闭环。

## 单公司研究

只有 `research_now` 才进入单公司队列。公司之间互相独立，可以并行；并发数由运行参数配置，通常可同时处理 3–6 家，但这只是资源调度，不是研究配额。

每家公司只交给一个 Agent。该 Agent 先快速浏览业务、财务、治理、估值和最新变化，再根据发现自行决定是否展开：

- 若很快确认不值得继续，停止扩展；`discard` 只要求一条非空的简短定性结论，关键逻辑、来源和公司特定重看条件都可省略。
- 若逻辑简单且没有实质变化，返回简版更新。
- 若机会真实、基本面可能变化或估值需要推演，再完成较完整研究。

不规定研究分钟数，也不按公司预先划分固定研究等级。研究投入由同一个 Agent 根据公司复杂度、信息质量和潜在价值自适应决定。

单个公司任务不拆给多人。Agent 领取任务后自行完成资料查找、判断和写作，只提交一次最终结果；过程中不设置另一名 Agent 复核、经理批准或往返讨论。协调器只负责派发独立任务、控制并发和统一写入共享状态。

正式报告以能支持下一步观察为准，重点包含：

- 一句话结论和关键投资逻辑；
- 最重要的正面变量与风险；
- 合理价值区间及主要假设；
- 值得重新关注的买入触发价；
- 会强化、削弱或推翻判断的后续财报与事件条件；
- 信息截止时间，以及可直接打开的来源 URL。

报告不要求仓位建议、自动交易动作或精确到虚假程度的收益率结论。价格触发只代表“值得重新看”，不代表自动买入。本流程到复看和排序清单为止，后续投资决定由用户作出，不再追加跨公司审批步骤。

正式报告统一叫 `current.md`，因为它表达的是“这家公司当前仍有效的判断”，不是另一条需要人工维护的日期时间线。信息截止时间和价格日期写在正文及公司状态中；每次更新的历史版本由 Git 保存。这样读取方永远只有一个明确入口，也不会出现日期最新但状态未同步的两套答案。

## 自选池

自选池由公司当前状态派生，不另建一套相互冲突的人工账本。通常纳入带有效触发条件的 `watch` 和 `researched` 公司，排除 `ignore`。初筛形成的 `watch` 至少保留证券代码、名称、观察理由以及一个价格或事件触发条件；完成正式研究后，再补齐关键逻辑、关键风险、合理价值区间、买入触发价、事件条件、最近研究日期和价格日期。

完成正式研究不等于永久留在池中：逻辑被证伪时可以移出，价格失去吸引力时继续保留但不提示，新的事实使原判断失效时更新报告和触发条件。池外公司也不是永久排除，重大变化可以让它重新进入判断流程。

## 每日收盘价格闭环

价格只在每个交易日收盘后扫描一次：

1. 获取并记录当日收盘价和日期。
2. 对自选池逐一比较有效买入触发价。
3. 只对首次跌入触发区间的公司产生提示；同一触发状态不重复提示，价格离开触发区间后才重新待命。
4. 主 Agent 对当天触发的公司做一次简短复看，检查价格、最新信息和原逻辑是否仍有效。
5. 按吸引力、确定性和变化程度排序，输出当天值得人工关注的清单。

每日扫描的输入必须覆盖当前所有带价格监控的 `watch` 和 `researched` 公司；缺少任意一家报价时整批报错，不更新部分触发状态。扫描器只返回价格命中，不创建研究任务。若只是价格变化且原逻辑有效，主 Agent 复看和排序即可；若同时出现实质性新信息，再通过 `research_now` 进入公司更新任务。

正式运行使用腾讯公开行情的一次完整、不复权收盘快照。`watchlist fetch-close` 只检查和展示报价；`watchlist run-close` 在全部证券身份、日期和收盘状态通过后才更新触发器。节假日或任一报价异常都按整批失败处理。

```bash
python -m trading_os watchlist fetch-close --date 2026-08-07 --at 2026-08-07T16:30:00+08:00
python -m trading_os watchlist run-close --date 2026-08-07 --at 2026-08-07T16:30:00+08:00
```

## 财报与重大事件闭环

财报、业绩预告、重大合同、监管处罚、控制权变化、资本结构变化等事件先进入全市场批量变化筛选，范围包含自选池内外的公司：

1. 程序找出自上次检查以来新增的事件和受影响公司。
2. 主 Agent 批量判断事件是否可能改变商业质量、现金流、风险或估值。
3. 没有实质变化的公司保持原状态，不写入本次状态变更，也不派任务；需要时只在本轮汇总中记一句。
4. 有观察价值但证据尚不足的公司进入或保留 `watch`，并写清下一触发条件。
5. 只有变化明显、值得重新判断的公司标记为 `research_now`，再派一个单公司 Agent 端到端更新。

因此，池外公司始终保留因新事实重新进入自选池的机会，池内公司也可以因证伪而退出。

`event` 模式只提交需要改变当前状态或标记为 `research_now` 的公司。三种路由含义与基线一致：`ignore` 会移出自选池，`watch` 会更新为观察状态，`research_now` 才创建单公司任务；不要用 `ignore` 代表“没有变化”。

公告采集使用巨潮官方证券目录解析当前全市场公司身份，再按自然日和公司块分页查询。单块超过官方 100 页上限、目录缺失、分页不完整、返回池外证券或 URL/稳定 ID 异常时，整批失败。

第一次运行必须显式给出起点；以后从成功检查点继续，并额外回看上一自然日，用近期稳定公告 ID 去除迟到披露和重叠结果。`events fetch` 将完整待判断列表写入 `tmp/`；主 Agent 判断其中全部公告，先用 `screen record --mode event` 写入确有变化的公司，再用 `events complete` 推进检查点。成功 ID 必须与 packet 精确同集，遗漏、重复或额外 ID 都不会写检查点。

```bash
python -m trading_os events fetch --since 2026-08-09T00:00:00+08:00 \
  --until 2026-08-09T07:30:00+08:00 --output tmp/event-packet.json
python -m trading_os events complete --packet tmp/event-packet.json \
  --input templates/event-judgments.json
python -m trading_os events status
```

## 运行与写入约束

- 主 Agent 可以分多批完成基线，但每一批都使用同一判断口径，且必须覆盖被冻结范围。
- 单公司 Agent 之间没有依赖关系；不要为等待另一家公司而阻塞当前任务。
- 单公司 Agent 不直接修改共享文件，只返回最终结构化结果；协调器按任务完成顺序串行写入状态、报告和自选池。
- 报告引用优先使用公司公告、交易所、监管机构等一手来源的公开 URL。稳定 URL可用时，不为审计形式长期保存重复下载文件。
- 每个已判断状态都要有简短理由。公司特定重看条件只在确实有用时记录；全市场财报与重大事件扫描始终覆盖 `ignore`，避免它变成永久黑箱。

## 当前版本清理

机制迁移时，只清理当前工作树中的旧流程文件、重复报告和不再需要的本地来源副本。先提炼仍有用的最新结论，再删除当前版本中的旧资产。

旧研报打捞固定读取只读标签 `pre-simplification-20260808`。候选必须绑定旧路径、Git blob 和当前证券身份；禁止整篇恢复、覆盖现有 `current.md` 或把身份错配的报告迁入。主 Agent先批量看候选，只把仍可能有价值的公司派给一个 Agent核验最新事实；垃圾、失效或错配资产直接放弃。

```bash
python -m trading_os legacy-salvage candidates --limit 100 --min-score 40
python -m trading_os legacy-salvage apply --input templates/legacy-salvage-decisions.json
```

本阶段不重写 Git 历史，也不强推远端；被删除内容仍可从历史提交恢复。等新机制稳定后，再以独立任务评估历史重写、仓库压缩和远端强推，不能把两件事混在本次迁移中。

## 验收标准

- 冻结范围内每家公司都有当前状态，且没有为 `ignore` 或普通 `watch` 公司错误创建单公司任务。
- 所有 `research_now` 都有唯一负责人和一个最终结果，不存在同公司多人研究或待审批节点。
- 自选池能从当前状态重建，触发价、事件条件和来源 URL 完整。
- 每日收盘扫描要求监控标的报价齐全，能去重、重新待命，只返回命中并支持主 Agent 输出简短复看后的排序。
- 财报与重大事件可以覆盖池外公司，且只有明显变化才产生单公司任务。
- 后续运行只处理新增和变化，不重复执行已完成的全市场基线。
